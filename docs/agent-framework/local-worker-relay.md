# Rehearse the local release relay

The relay is a manually launched exact-H lane for an independently reviewed PR. Peter owns the first production invocation. Install and rehearse the control plane separately from the application candidate. A relay receipt proves release state for one attempt. Issue closure and the project delivery record still follow the existing project workflow.

## Prepare the protected Worker and VPS

1. Freeze an exact reviewed relay source commit and the Python, Git, curl, OpenSSH, nginx, and systemd inputs used by the installed profile. Install the protected source at `/opt/dailycheck-relay/authority` on each host. Keep the source and its parents unwritable by SSH ingress and application users. Verify the file pins before exposing the ingress. Put the exact source SHA and the per-file SHA-256 manifest in the private adoption record.
2. Install `deploy/scripts/dailycheck-relay-worker` as the fixed local entry point. Pin `/opt/dailycheck-relay/worker-python` to the approved Python 3.10+ installation. Use a protected Worker identity to run it. Store `/etc/dailycheck-relay/worker.json` and the source binding, Worker ledger, private keys, and known-hosts file under protected ownership. Pin the local auth executable and its approved installation ID.
3. Install `deploy/scripts/dailycheck-relay-ssh` as a root-owned command. Assign a dedicated ingress account and a single pinned SSH public key. Configure `restrict` and a forced command for the key and for the user in sshd. Deny PTY, forwarding, agent use, and alternate login methods. If the approved path uses sudo, grant only `/usr/local/sbin/dailycheck-relay-ssh ""` and preserve only `SSH_ORIGINAL_COMMAND`. The wrapper checks the original command and clears the environment.
4. Enforce the VPS relay process boundary before enabling ingress. Inventory all historical release credential locations and mask them from the relay and the app units. Verify that the caller, application identity, and Git subprocess cannot read the former issuer, a GitHub token file, or any inherited release credentials. The existing systemd service launchers must preserve the fixed stage helpers, interpreter, database paths, and access logs. Verify these conditions from the actual process and service configuration.
5. Generate independent SSH transport and Ed25519 authority keys on the Worker. Install only the authority public key in the VPS allowed-signers file as principal `dailycheck-local-release-worker`. Verify both fingerprints. The same private key must not serve both purposes.
6. Populate `/etc/dailycheck-relay/vps.json` with the protected control paths. Preserve the existing `.attempt.lock` and `.state.lock` in the deployed state directory. Record their device and inode. Confirm the historical watcher and webhook remain disabled, there is no active native queue, and legacy executors respect the guard. Keep manual blue rollback under Peter's control while the relay owns the fence.
7. Approve only the canonical anonymous HTTPS Git proxy in the VPS profile. This profile accepts a fixed proxy origin without user information and clears ambient Git and proxy configuration. If no approved anonymous proxy is available, leave that field absent for bundle-only ingress. Proof of Mac HTTPS fetch does not establish VPS HTTPS access.

The VPS needs a protected bare seed containing the exact B object graph and protected blue runtime evidence at B. If green is serving B before admission, supply its exact protected runtime path too. The built-in observer requires separate root-owned immutable release trees, app and MCP systemd processes at those paths, and current route and access-log proof. The legacy B layout, actual unit names, ingress account, approved credential masks, live file pins, and optional canonical proxy still need Peter's readback. An unsealed B installation fails before candidate stages.

Both profiles use a `target` with `pr`, `pr_id`, `pr_node`, `head`, `base`, `ref`, `tree`, `attempt`, `generation`, and `source`. The last is the digest of the protected source binding. Resolve the current production source privately on both hosts. Use a new 32-hex attempt and the top-level state generation plus one. Keep the rendered profiles private.

Use the protected `pipeline` schema in [the existing protected executor](../../scripts/prod_agent/native_pipeline.py). Its helper and tool entries are hashes of installed bytes. Use its application environment schema for app data-plane settings. Keep release credentials outside that file. The relay has no VPS issuer input. Verify its access to the approved nginx config, the instance-specific app access logs, and the B and H service identities.

The pinned local auth executable reads one JSON object on standard input. It accepts the exact target and one phase from `preflight`, `merge-read`, `finalize`, `reconcile`, `reject-read`, or `abort-read`. It must verify the approved App and installation, issue a fresh role-specific token restricted to the public code repository ID, and return the target, phase, `repo_id`, `installation_id`, integer epoch `expires`, and `token` on stdout. The read roles require access to their live checks and protection facts. The `finalize` role needs the existing exact non-forced atomic ref permission, with original protections still enforced by GitHub. Reviewer access and authorization stay separate from the issuer's decision. Provisioning the approved local issuer and proving actual scopes is part of adoption.

## Run a docs-only pilot

1. Reuse the coordinator's separate candidate from current live main after independent review. Re-read its exact PR node, title/body, H, B, candidate tree, branch, and trusted CI. Confirm the delta is a single low-effect explanatory documentation change. Keep #43 and the unresolved historical evidence archived.
2. Under a separately authorized trial, run the Worker `status` from the protected local host. Validate that the fixture flags are unavailable through both installed wrappers. Exercise a read-only wrong-target denial and the SSH forced-command denial before sending a valid `start`.
3. Run `start`. Watch the same attempt via `status`. A transport acknowledgement only confirms admission. Read the source method, stage result, original production anchor, switch evidence, runtime identity, and the completed real observation of at least 600 monotonic seconds.
4. If the observation receipt and review remain valid, run `finalize`. The Worker renews auth locally, reads the exact GitHub and VPS facts again, and records intent before the single atomic write. Preserve the final readback and the native deployment receipt.
5. For a write response of uncertain effect, run `reconcile` with qualified fresh read-only authority. If the exact merged PR and main cannot be corroborated, retain the guard. A durable definitive 401 or a locally proven pre-POST failure requires a fresh matching open PR and main B before the Worker signs rollback. For other GitHub errors without authoritative no-write evidence, record uncertainty.

The current task's authorization permits isolated tests and local evidence only. Activate the production command and first invocation after Peter has the approved identity and ingress readbacks and independent review. This guide does not itself grant access or change the existing release gates.

## Remove the pilot ingress

After a verified terminal result, revoke the dedicated SSH ingress key and the Worker authority key for this pilot. Restore the prior ingress settings through Peter's approved config rollback and compare their pinned bytes. Leave the old watcher and webhook disabled. Preserve deployment outcomes and stage evidence. If the attempt is unresolved, revoke new admission while retaining the private ledger, route facts, and shared guard. Do not clear the state files or rerun the candidate to release the fence.

The source sets a real 600-second production minimum. The OpenSSH integration tests use a one-second observation fixture and isolated route and GitHub doubles. Existing Linux tests exercise the blue/green helpers against controlled service and database fixtures. Neither fixture establishes the VPS's installed layout.
