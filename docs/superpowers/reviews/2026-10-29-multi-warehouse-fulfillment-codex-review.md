## P0：实施前必须解决的数据一致性问题

### P0-01：跨文件扣库与订单记账之间没有可恢复提交协议，失败重试可重复扣库

**问题**：设计第 7 节只把扣库位置由头仓改到来源仓，并宣称累计逻辑不动，没有定义仓库库与主库之间的提交、幂等和恢复协议。当前流程先永久扣库存，再写配送批次和已发数量；后半段失败，回滚主库无法恢复已提交库存。多仓同时发货会提高主库竞争和批次号冲突概率。此缺陷原已存在，本设计把它带入常态并行路径，不能作为“沿用”项放过。

**证据**：

- 设计 `docs/superpowers/specs/2026-10-29-multi-warehouse-fulfillment-design.md:93` 仅要求在行来源仓扣库。
- `blueprints/store_ordering_pure.py:1760` 在事务保护之前读取订单；`:1832` 把库存写为计算得到的绝对值；`:1845` 提交仓库库。
- 同文件 `:1854` 才生成批次号，`:1856` 才插入批次，`:1876` 写已发数量，`:1915` 才提交主库；`:2359` 的批次号由“读取当天最大号再加一”生成，主库 `db/__init__.py:570` 又有唯一约束。
- 收货同样跨文件：`blueprints/store_ordering_pure.py:2087` 插入主库收货记录，`:2186` 先提交门店入库，`:2242` 才提交主库。收货失败重试也可能重复入库，不能笼统承诺“收货累计逻辑不动”。
- 内存故障注入：给配送批次 INSERT 加一个失败触发器，调用真实 `_ship_order_partial_impl`，随后回滚主库，结果为“仓库库存 9、出库流水 1、配送批次 0、已发量 0”（初始库存 10、请求发 1）。

**建议**：在实施设计中选择并写清一套提交协议。可以评估单连接挂载主库与本次来源仓库后共同提交，但必须核对实际 SQLite 日志模式、文件系统与跨文件原子性条件；不能仅写“加事务”就宣称解决。若继续使用独立连接，则需要持久操作号、仓库侧操作号唯一约束、主库执行状态、崩溃后补记/补偿与对账恢复程序。发货和收货均使用客户端重试可复用的幂等键；扣库须在锁内重读或使用带库存条件的原子扣减，防止并发绝对值覆盖。无库存预留的 D9 不禁止实际发货时使用短事务锁。

验收至少覆盖：仓库提交后进程退出、主库批次 INSERT/COMMIT 失败、请求响应丢失重试、同仓两单竞争库存、收货入库后主库失败；库存流水与批次明细必须能按操作号核对。

## P1：设计契约存在阻断缺口

### P1-01：多仓并发聚合仍使用旧订单快照，发齐后可能永远不转 shipped；取消也有检查后竞争

**问题**：A、B 各自在订单仍未发货时取到快照，然后分别完成自己的最后一行。各自计算全单状态时都认为对方未发齐，最终所有行已发齐，订单仍停在 approved，没有全发齐通知，后续收齐也无法正常进入 delivered。同一行重试会覆盖累计数。取消在检查“未发货”后与发货竞争，也可能把已经实际出库的订单取消。

**证据**：

- 设计 `:96` 写“`fulfilled_quantity` 按行累计”用于超发判断，但实际**已发量是 `shipped_quantity`，`fulfilled_quantity` 是已收量**；`blueprints/store_ordering_pure.py:1789` 和 `:2201` 分别证明两者含义。
- `blueprints/store_ordering_pure.py:1885` 从函数入口的 `order['order_items']` 构造全单已发集合，仅覆盖本请求操作的行；`:1892` 据此判定全发齐。`:1877` 也使用绝对量更新而非带版本校验的累计更新。
- 同文件 `:2225` 只有全收齐且主状态已为 shipped 才转 delivered；`:2298`、`:2313`、`:2321` 的取消检查与更新不在一个明确的锁定协议内，更新没有当前状态条件。
- 确定性交错验证：请求 A 读取两行均为 0 的快照后暂停，B 发齐第 2 行并提交，再恢复 A 发齐第 1 行。真实核心最终得到“已发量 [1, 1]、批次 2、主状态 approved、转 shipped 的历史 0”。这是已有快照算法的复现，多仓来源选择尚未实现。

**建议**：把订单修改作为同一个受保护的操作：先取得数据库级写锁/订单版本，再重新校验状态、权限、来源和待发量；写完累计数后，在同一事务中从数据库重新聚合全部行。通过条件状态迁移和唯一事件键保证只有一次 approved→shipped 和一次通知；取消、审批、发货、收货遵守统一锁顺序。明确数量不变量 `0 ≤ 已收 ≤ 已发 ≤ 订购`，并将历史 v2 的“shipped 且无已发数时回落订购量”限制在可识别的历史数据，避免新异常数据被当作已发。保留 approved 时按行收取实发量的能力，见 `:1940`、`:1968`、`:2079`，不要新增“整单 shipped 才可收”的门禁。

### P1-02：示例回填不是幂等迁移，重跑会把已固化的跨仓来源覆盖成主仓；调货新写入也不会自动兼容

**问题**：文档给出的 UPDATE 没有只填空值条件，重跑会改写已经建好的跨仓单，违反“路由提交后固化”。新增列可空且没有默认/触发器，现有调货建单函数不会写来源仓；一次性历史回填无法覆盖迁移之后新建的调货单。“调货逻辑零改动”与其新写入要求矛盾。购物车兼容列同样是 NOT NULL 外键，去掉选仓后如何创建新购物车未定义。

**证据**：

- 设计 `:53` 无条件回填；`:59` 要求调货新建行写头仓；`:60` 却宣称模块逻辑零改动；`:67` 要求历史订单来源固化。
- 内存执行设计原 SQL：原始来源 A、B，头仓 A，执行后变成 A、A。
- `blueprints/dc_transfer_pure.py:202` 的 INSERT 仅写旧明细字段；`db/__init__.py:461` 的购物车头仓不能为 NULL；`:464` 的唯一键是**用户＋门店**，不是每店所有用户共用一车。
- `docs/ARCHITECTURE.md:1255`、`migrations/__init__.py:7` 要求新增 schema 进入版本化迁移注册表；设计 `:125` 仅提“一次性脚本”。

**建议**：采用正式迁移条目、备份、事务和版本门控；只回填 NULL 的来源/批次仓，且重跑不得覆盖已配置路由。明确旧数据异常检查和回填后校验。调货建单必须做最小适配，或由统一建单层显式填来源，业务页面和断言可以保持原语义。为新购物车定义合法的兼容列写值和废弃边界，保留现有“每用户每门店”车语义。验收包含“先迁移→创建跨仓单→再跑迁移”和“迁移后新建调货→发货→收货”，不能只在空库连续跑两次。

### P1-03：加列兼容不等于业务兼容，蓝绿灰度和回滚期间旧程序会把跨仓单当主仓单处理

**问题**：D8 保留主仓头字段让旧代码可以继续读取，却也让旧发货程序继续按头仓扣所有行。灰度时新实例建跨仓单，后续请求可能落旧实例：非主仓人员看不到，主仓人员却可能从主仓的同 canonical 镜像行错误发货。新代码回滚后问题同样存在，不能用“加法式，无破坏”概括上线风险。

**证据**：

- 设计 `:31`、`:34`、`:125` 未规定多仓功能开关、旧写者退出或回滚后的业务隔离。
- `scripts/blue_green/promote.sh:21` 将新实例指回真实数据库；`scripts/blue_green/switch.sh:7`、`:8` 的 5%/50% 灰度允许新旧实例同池处理请求，`:10` 支持切回旧实例。
- 现有 `blueprints/store_ordering_pure.py:1801` 只打开头仓库；`:1811` 按 canonical 在该库找品项。主数据多仓镜像存在时，错误发仓可以不报“找不到品项”。

**建议**：设计分阶段发布：先让全部读写者具备识别多仓能力或能拒绝多仓单，再开启跨仓建单；灰度阶段可先关闭跨仓创建。写明旧客户端、Flask、MCP、后台脚本和回滚目标版本的能力边界。产生首张跨仓单后，回滚旧业务代码必须有经验证的隔离策略，不能把新增来源字段删掉或回填成头仓来“兼容”。本评审不授权修改部署流水线；若需要改其行为，按项目红线另行取得授权。

### P1-04：路由播种使用不存在的字段，且“唯一持有”不足以证明供货归属；租户和仓类型契约缺失

**问题**：仓内没有 `binding_active` 列。若扫描全部仓，只在研发镜像持有的品项也会被判成“唯一持有”并路由给研发仓，而发货入口仅允许 DC；门店专属标记是本地行属性，也不是 canonical 的全局属性。即使唯一一个 DC 持有，也可能只是扇出生成的空库存镜像，不能天然等于经过业务确认的供货责任。新增 `tenant_id` 只做复合主键，未保证 canonical、目标仓、下单门店与路由租户一致。

**证据**：

- 设计 `:41` 的两个外键仅验证 ID/code 存在，不能验证租户相等、仓类型和供货资格；`:56` 提“binding_active 有效”和扫描各仓。
- `db/__init__.py:1588` 至 `:1617` 的真实字段为 `canonical_id/is_alias/canonical_status/is_store_exclusive/is_active`；`blueprints/canonical_pure.py:2436` 明确绑定启停实际写 `items.is_active`。
- `blueprints/canonical_pure.py:2378` 的已绑仓支持 storefront、rd、DC；`:1905` 的扇出会创建数量为 0 的镜像。
- `blueprints/store_ordering.py:1066` 限发货入口为 DC；`docs/ARCHITECTURE.md:1707` 明确研发中心无库存业务。
- `db/__init__.py:120`、`:333` 有仓与 canonical 的租户字段；`docs/ARCHITECTURE.md:1550` 明确现有订单/扇出等租户过滤尚属未覆盖范围。`blueprints/store_ordering_pure.py:216` 仍按公共目录拼仓库文件，而其他租户仓放置规则见架构 `:1549`。

**建议**：明确播种候选只来自同租户、可履约类型的 DC，绑定有效按真实字段定义，门店/研发/专属行不得自动成为发仓。保守地把“唯一合格 DC”生成为待确认建议；若坚持自动启用，需说明为何唯一镜像足以代表供货责任，并生成可审计清单。管理接口、提交与发货都校验租户、仓类型和路径，不接受仅凭外键存在的配置；若一期只支持租户 1，应显式拒绝其他租户，而非看似支持却访问错文件。播种后新扇出/claim 不得暗中改路由。

### P1-05：唯一来源仓没有解决本仓多绑定与单位冲突，沿用 dc_item_id 回填会选错实际扣库行

**问题**：设计识别了“一品多仓”，但漏了“一仓多行”。只确定仓 code 后继续 `fetchone()`，可取到别名、停用行或单位冲突行；价格、倍数和可用库存也可能与实际扣库行不一致。claim/unclaim、停用和扇出以后，路由记录还在但履约行可能消失、改绑或冻结，设计没有就绪态和处置规则。

**证据**：

- 设计 `:93` 说 `dc_item_id` 回填逻辑不变。
- `db/__init__.py:1616` 只是普通 canonical 索引，没有 `(canonical_id)` 唯一约束。
- `blueprints/canonical_pure.py:1539` 只检查当前行是否已认领，不禁止另一个本地行认领同一 canonical；`:1552` 单位不符只记录冲突、不阻断认领；`:1665` 显式处理同 canonical 的多行绑定。
- `blueprints/store_ordering_pure.py:1104`、`:1128`、`:1810`、`:2110` 都按 canonical 取首行；详情 `:1380` 又按仓内 item ID 查询。item ID 只有与正确仓 code 配对才有意义。

**建议**：在保持 canonical 扇出架构不变的前提下，定义履约专用解析器：在指定来源仓内解析唯一、有效、单位可比且无阻断冲突的扣库行；有多个候选则要求配置明确行或执行已约定的聚合/分摊规则，不能依赖首行顺序。价格、倍数、发货、详情都使用同一解析结果。对已建单的仓来源保持固化，同时明确本地解绑/停用后的失败关闭、修复或受审计替代流程，禁止静默换仓。提交和发货均验证就绪，但仍不检查/预留库存到建单阶段。加入同仓重复绑定、单位不符、来源解绑重绑、跨仓相同 item ID 的验收。

### P1-06：目录“有路由即可见＋专属品并集”丢掉可订门禁，专属品也无法满足提交规则

**问题**：有路由不代表可订。照第 4 节字面实现，会重新显示主数据停用品、来源仓下架品和本店停用品，绕过既有门禁；将本店专属品无条件并入目录又与 D6“每行必须有发仓路由”、门店专属不播种矛盾。购物车中留存的旧选择和提交时路由改动，也可能导致价格/倍数取旧仓、最终来源取新仓。

**证据**：

- 设计 `:70` 至 `:73` 仅按路由和专属品定义目录；`:57` 把门店专属放待配置；`:66` 对每行强制路由。
- 现有 `blueprints/store_ordering_pure.py:537` 过滤主数据 active，`:555` 要求 DC `is_orderable=1`，`:575` 排除本店停用；架构 `:1733` 至 `:1743` 说明目录与本店库存口径。
- 同文件 `:316`、`:333` 从车头仓读取价格与倍数；`:1197` 还校验本店绑定，`:1233`、`:1237` 分两次取验证和购物车，`:1244` 据此算运费。

**建议**：把已配置路由作为原有目录门禁的附加条件，保留主数据总闸、本店启停、来源仓可订和起订倍数四道校验；未路由品项默认不进入可提交目录是合理方向。请产品明确专属品是自采库存还是要 DC 配送：自采品不要加进 DC 订单；需配送品仍须显式合法来源，不能因专属标记豁免 D6。明确本店未绑定是否仍阻断提交。提交时一次性解析并复用路由、履约行、倍数和价格快照；路由变化导致价格/倍数变化要给门店重新确认的契约。

### P1-07：全仓审批无法直接复用当前仓权限缓存，拒绝/取消与旧发货兼容入口仍有授权缺口

**问题**：D5 需要跨来源仓逐个解析权限，现有权限函数只解析当前仓。简单循环调用 `has_permission()` 会在每个仓重复使用同一权限集合。当前审批展示还用角色名而非权限点；拒绝与批准共用入口，文档只给批准加全仓限制、却要求拒绝“维持现有守卫”，跨仓整单拒绝和取消到底由谁决定未明确。发货除了显式行 ID 表单，还有无字段自动全发和旧 qty 字段，不能仅对新表单做隔离。

**证据**：

- 设计 D4/D5 位于 `:27`、`:28`，拒绝/取消口径在 `:84`；`:92` 只提越仓行 ID 拒绝。
- `permissions.py:62` 复用 `g.perm_set`，`:90` 查询固定 `g.warehouse['id']`，`:111` 的 `has_permission()` 不接受目标仓参数。
- `blueprints/store_ordering.py:715` 的 `can_review` 仍取 manager/admin 角色；`:885` 入口校验当前仓 `order.approve`；`:898` 又按头仓约束。`:1044`、`:1047` 的取消也硬编码角色与头仓。
- `permissions_manifest.py:351` 的看板入口仍是 DC＋staff 阶梯守卫；`permissions.py:161` 阶梯判定与权限点不是同一语义。
- `blueprints/store_ordering.py:1117` 会把旧 qty 应用于所有未发齐行；`:1133` 无明细字段时自动全发；`blueprints/store_ordering_pure.py:1708` 的全发 helper 遍历全单，未接受当前来源仓。

**建议**：新增可指定目标仓的权限解析能力，使用与现有 RBAC 相同的内置/租户角色规则并失败关闭，请求缓存按用户＋仓＋租户分键；D5 的后台校验和缺权说明共用结果。明确整单拒绝、审批后取消是否也要求全仓权限，或由哪类单仓角色拥有整单否决权，并把实际决定写入角色/动作矩阵。保留 DC staff 既有发货能力，不要顺手改成其未持有的 `order.ship`。所有发货入口必须明确一个服务器端确认的来源仓并只操作该仓行；平台管理员也不能在一个批次里混发多个仓，需定义其操作仓如何确定。同步权限矩阵和模板门禁，覆盖伪造行 ID、空表单、旧 qty、后台直接调用、平台管理员与仅部分仓授权。

### P1-08：主仓兼容会静默漏单，查询范围不能只改订单板和 MCP 列表

**问题**：头仓装不下多仓参与关系。健康报表完全遗漏非主仓的积压/在途/履约周期；MCP 有列表、总数、详情三套独立可见性，修改其中一处会出现“列表有、详情无”或 total/truncated 错误。新订单查询若把头仓继续作为无条件可见性兜底，也会掩盖缺来源数据，而非真正兼容。

**证据**：

- 设计 D8 `:31` 宣称旧报表/MCP 过渡兜底；`:113` 把头仓并入可见集合；影响矩阵 `:119` 只点名订货报表，遗漏健康报表。
- `reports_health_pure.py:388`、`:393` 的两条 SQL 都只看头仓或门店仓；未读取明细。
- `mcp_server/service/store_order.py:130` 展开多次列表查询，`:160`、`:167` 自写计数条件，`:186` 自写详情可见性。它们不会因底层 `list_orders` 改变而自动全部兼容。
- 其他旧依赖包括 `blueprints/store_ordering.py:128` 的详情/付款凭证可见性、`:134` 的操作守卫，以及 `store_ordering_pure.py:1498` 的状态计数。
- 内存验证同一订单头仓 A、行来源 A/B：健康报表 A 积压=1、B 积压=0；现有 MCP `_is_visible` 对仅 B 授权返回 False。

**建议**：引入统一的“订单参与仓”谓词，使用 EXISTS 避免多行 JOIN 把整单翻倍；按门店、来源仓、历史空字段兜底定义清楚。兼容头仓用于历史无来源单或显示标签，不再宣称能替代参与仓。同步列表、分页、计数、详情、附件下载、健康报表、状态页签与深链守卫。MCP 明确“参与一个仓即可读全单”的信息范围：这会让 B token 读到 A 行、金额、收货历史，属于 ACL 扩展，需要在契约中说明并测试，不能只测试查得到。至少覆盖 B-only token、显式 B 过滤、空范围、A/B 都授权去重、多页和 list/detail/count 一致性。

### P1-09：订货报表的订单数与运费是头级事实，仅把筛选改成行级会漏算或重复计费

**问题**：“按仓筛选改行级”没有定义报表各指标粒度。数量应归来源行，订单数在全局应去重、在参与仓维度可能各计一次；运费目前是一单一次，若 JOIN 明细后直接 SUM 会随行数重复，若仍按头仓只算则非主仓少记或归属失真。分类筛选叠加也必须与订单集合一致。

**证据**：

- 设计 `:119` 仅说 `compute_store_order_report` 按仓改行级。
- `blueprints/store_ordering_pure.py:930`、`:942` 的数量分组仍取头仓；`:1040` 到 `:1058` 另从头表统计订单数和运费，最后把各组计数相加。`:1030` 只会移除 ci 谓词，若直接加入 soi 来源条件，后面的头表查询甚至没有 soi 表可引用。
- `db/__init__.py:1108` 的 `shipping_fee` 在头表，`store_ordering_pure.py:1245` 提交时整单锁定。

**建议**：先明确仓维度运费采用主仓记账、按比例分摊，还是仅展示全单费用且禁止跨仓求和；不要默默选择财务语义。实现上分离“过滤后明细集合”和“去重订单集合”，分别算数量与头级事实。验收例：同单 A 两行、B 一行、运费 10；全局订单数=1、全局运费=10，A/B 的数量准确，仓维度费用满足已确认规则；分类/日期/仓组合过滤同样成立。

### P1-10：补货看板与采购邮件并非无影响，同 canonical 多 DC 镜像会重复承接全部门店需求

**问题**：D3 明确允许同品项多仓持有，但现有补货计算把该品项的全部门店需求用于每个持有它的 DC，同时把各 DC 的可订开关合并为一个以 canonical 为键的字典，后遍历的 DC 会覆盖前面的。引入显式路由后继续使用旧算法，会向非来源仓建议备货，甚至多个仓都向供应商采购同一份需求。目录改对了也不能保证采购建议正确。

**证据**：

- 设计 `:26` 承认多仓绑定，`:123` 却明确标记预测/采购建议无影响。
- `blueprints/replenishment_data.py:650` 到 `:661` 聚合所有门店需求；`:695` 到 `:702` 无来源判定地写 `dc_orderable[canonical_id]`；`:732` 到 `:734` 对每个 DC 使用相同下游需求序列。
- 同文件 `:747` 到 `:769` 仅依赖各 DC 的 `is_orderable` 过滤，未读路由。
- `blueprints/procurement_digest_pure.py:110`、`:124` 到 `:138` 会选择所有符合条件的 DC 行进入供应商采购建议，没有按路由去重。

**建议**：将补货看板、采购邮件及其数据装配纳入影响面。门店需求应只拉动配置中的来源仓；非来源仓的既有库存与人工调拨需求单独保留，不重复拉动采购。门店可订开关也从实际来源仓解析。不能要求人工永久保证其他镜像仓全部下架来弥补系统缺口；若一期确实采用该运维约束，必须做发布前机验并限制配置。测试两个 DC 都有同 canonical 且可订、路由仅指向 B，采购拉动只能在 B 出现一次。

## P2：需要补齐的审计、通知与交互契约

### P2-01：配送批次只有仓归属，没有批次明细，难以审计多仓分批货物与收货对应关系

**问题**：新增批次仓只能知道“这批从哪里发”，不能知道“这批各发了什么、多少”。行累计数不能还原多次批次构成，且每个仓库流水只把订单号写进 note。普通行级累计收货可以继续工作，不必强制收货按批次；但发货操作审计和 P0 所需故障恢复不能只依赖累计字段和文本。

**证据**：`db/__init__.py:567` 的 deliveries 没有子明细；`:587` 的 receipts 只关联订单行；`blueprints/store_ordering_pure.py:1842` 的出库 note 只有单号和数量；设计 `:94` 只新增批次仓。现有 `:2233` 在整单收齐时给所有批次写相同 delivered_at，并不表示每批实际到货时间。

**建议**：为批次增加不可变行明细（批次、订单行、来源仓、本地 item、实发数量、操作号），或设计等价的可关联流水。明确批次 delivered_at 仍是整单完成派生时间，若要展示物流批次完成则另建对应规则。测试多仓同日多批后能按操作还原库存和发货；收货不增加批次关联时，明确不能声称已支持批次级签收追踪。

### P2-02：通知改造表述与当前事件方向不一致，按角色名选收件人也不等于持有审批权限

**问题**：设计说“审批事件从头 DC 审批人扩成各来源仓审批人”，但当前**提交事件**通知 DC，**批准事件**通知门店。按字面替换会误改方向，漏掉门店批准通知。D5 要全仓权限，多个来源仓审批人的并集又可能没有任何一位能真正审批。仍按 manager/admin 角色收件会漏掉被授予权限的其他角色，或通知已被撤权的人。

**证据**：设计 `:86`；`blueprints/store_ordering_pure.py:2388`、`:2392` 区分提交/批准；`:2409` 的部分收货和 `:2413` 的取消也调用 DC 收件函数；`:2443` 固定角色集合。当前企微 `blueprints/wecom_notify_pure.py:75` 到 `:114` 是固定 markdown 标题、单号、门店、计数、时间、链接，并没有设计所称需追加行字段的结构化业务 payload。

**建议**：逐事件列收件矩阵：提交、批准、拒绝、部分收货、全发齐、取消和调货分别确认方向；提交时可通知参与仓并集，但要区分“知会”和“可审批”。以有效权限解析收件人，并为不存在全仓审批人的单明确管理告警。全发齐通知必须由 P1-01 的唯一迁移结果触发。企微若保留现有摘要则通常无需暴露跨仓明细；如增加信息，应明确消息模板契约，不泛称 payload 轻改。

### P2-03：前端草稿键仍按 DC 分区，去 DC 后会串店或复活已消费的选择；主仓同点规则也缺最后稳定键

**问题**：去掉 selected_dc 后现有草稿键会退化成“用户＋空 DC”，同一用户在不同门店可能复用选择。若改 catalog 的键而漏改 cart 的消费清理，又会导致回退重复加购。D8 同行数时按仓创建时间排序，如果时间也相同，仍没有唯一确定结果。

**证据**：`templates/store_ordering/catalog.html:185`、`:186` 使用 `用户:DC` 草稿键；`templates/store_ordering/cart.html:79` 到 `:81` 按同键清理；架构 `docs/ARCHITECTURE.md:1773` 到 `:1779` 规定跨筛选草稿、批量消费和 bfcache 同步必须联动。设计 `:62` 只废弃 session 键，`:123` 标“门店 PWA 交互无影响”；`:31` 的主仓平局规则只到创建时间。

**建议**：草稿键升版为“用户＋门店仓”，同步恢复、消费、清空和 pageshow 处理，定义旧 DC 草稿迁移/丢弃提示并校验已失效品项。购物车保留每用户每门店语义。主仓排序明确最后按 code 或 id 排序，并固定使用哪个实体的创建时间。验收同用户切换两家门店、跨分类加购、路由删除、回退和两仓相同创建时间。

## 建议补入修订稿的验收矩阵

| 领域 | 必须可观察的结果 |
|---|---|
| 数量与事务 | 任意失败点后，操作可按唯一号恢复；同请求重试只扣/加一次；两单抢库存不超扣；收发与取消竞争不能产生已取消在途单 |
| 并发状态 | 两来源仓同时发最后一行后，整单 shipped 一次、事件一次；A 发/收时 B 仍未发，订单维持 approved 且 A 可收；最终收齐 delivered 一次 |
| 路由 | 研发镜像、跨租户、专属自采、无本地行、重复绑定、单位冲突均得到明确结果；路由改动不改历史来源，旧车重新验证 |
| 可见与动作 | B-only 用户/token 看得到参与单；list/detail/count/附件一致；缺任一来源审批权限不能批准；越仓行、空表单、旧 qty 不越权 |
| 迁移与发布 | 跨仓单建好后重跑迁移仍保留 A/B 来源；迁移后调货正确写来源；旧版本承流/回滚无法误发跨仓单 |
| 报表与补货 | 多仓筛选数量正确，订单/运费不重复，非主仓健康指标不漏；同品项只有路由仓承接门店采购拉动 |
| 前端与通知 | 同用户不同门店草稿隔离，回退不重复加购；提交/批准/收货/取消收件方向正确；没有实际全仓审批人时可诊断 |

## 总体结论

**需修订后实施。** “一单多仓批次＋行级来源快照＋独立显式路由”可以成立，无须因为本次评审改成拆订单或重做 canonical 扇出；但当前稿把跨文件一致性、并发聚合、业务兼容和多仓采购拉动当作旧逻辑沿用，缺少可安全实施的边界。

进入实施计划之前，应先消解 P0-01，并将所有 P1 的提交协议、状态/权限矩阵、路由就绪规则、查询粒度、迁移和发布策略写进修订稿；P2 若不本期实现，也要明确其能力边界，避免对外承诺批次级追踪或前端无影响。目录未决项建议采用“已路由且满足既有可订门禁”作为默认，专属品、自采、仓维度运费及整单否决权保留产品明确决策，架构评审不代替业务拍板。

本任务仅交付设计评审报告，未创建 PR 或 Issue、未运行 CI、未合并或部署；没有可宣称的生产交付状态。
